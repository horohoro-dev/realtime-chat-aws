# HTML による説明ドキュメント

## 文章

説明内容と日本語表現を補うため、次のスキルの併用を推奨する。

- `explain`：概念や仕組みを説明するときの用語定義、説明の粒度、構成
- [`japanese-tech-writing`](https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d)：日本語の技術文書、記事、解説文の構成と文章規範
- [`cognitive-rhythm-writing`](https://gist.github.com/k16shikano/eb2929f13ed19c97188393d297be8432)：読み物としての緩急が必要な長文の文章規範

いずれも推奨スキルであり、`html` の必須依存ではない。
`stop-ai-slop-jp` だけは必須で、「仕上げの点検」の工程で使う。

### レポート単体で読める文章にする

読み手は、作成時の会話を見ていない第三者（採用担当、チームメンバー、数か月後の自分）と想定する。
HTML だけを開いた人が、前後の事情を知らなくても内容を理解できるように書く。

書かないもの:

- 会話の経緯：「途中で一度〜と説明しましたが、撤回しました」「先ほどの案」「ご指摘のとおり」「前回の版では」
- 依頼者への呼びかけ：「あなた」「ユーザー」。登場人物は「管理者」「開発者」「レビュアー」のような役割名にし、初出で何を指すか定義する
- 作業者の視点：「今回は」「今のブランチ」「手元で確認したところ」。事実として書き直す（例：「`feature/x` ブランチで〜を進めている」）
- 会話の中でしか決まっていない略語、仮の呼び名、案の番号（「案B」「さっきの構成」）
- 「〜してください」のような、文書の読み手ではなく依頼者に向けた指示

方針を変えた結果を書くときは、変更の経緯ではなく、採った案と採らなかった理由だけを書く。
修正依頼で既存の HTML を直すときも、修正の経緯を本文に残さない。

## 成果物

- HTML を作る
- ビルドなしでブラウザが直接描画できる状態にする
- 保存先はリポジトリルートからの相対パス `docs/reports/{テーマフォルダ}/` とする。現在の作業ディレクトリには左右されない
- `docs/reports/` 直下には HTML を置かない。まとまり（テーマ）ごとにフォルダを分ける
- 作成前に `docs/reports/` の既存フォルダを確認し、内容が合うテーマフォルダがあればそこへ保存する
- 合うフォルダが無ければ、内容を表す短い英語のケバブケース名（例: `realtime-chat`、`rds-proxy`）で新しく作る
- テーマフォルダ内でさらに分類が必要な場合は、サブフォルダを切ってよい（例: `realtime-chat/infra/`）
- ユーザーがその依頼の中で別の保存先を明示した場合だけ、そちらに従う
- ファイル名は `{yyyymmdd}-{内容を表すケバブケース}.html` とする。既存ファイルの更新では名前を変えない
- 個別の文書管理システム、メタデータ、Viewer、公開先に関する規則は、このスキルを参照する上位スキルの指示に従う

## デザインシステム

作成前に `design-system/component-samples.html` を確認する。コンポーネント集は `design-system/document.css`、ライト / ダーク切替は `design-system/theme.js`、数式コピー機能は `design-system/math-copy.js` を正とする。

共有アセットはテーマフォルダごとに `docs/reports/{テーマフォルダ}/design-system/` を一つ置き、そのフォルダの成果物から次の相対パスで読み込む。
このディレクトリが無い場合だけ、スキル内の `design-system/` をコピーして作る。既にある場合はコピーし直さず、成果物ごとに複製もしない。
ただし既存の `design-system/` に `theme.js` が無い場合は、スキル内の `document.css` と `theme.js` で置き換え、そのフォルダの既存 HTML の head に `theme.js` を追加する。
サブフォルダに置く成果物は、`../design-system/` のようにテーマフォルダの共有アセットを参照する。
テーマ固有の追加スタイルが必要な場合は、テーマフォルダに `{テーマ名}.css` を置いて `document.css` の後に読み込む（例: `面接対策/interview.css`）。
上位スキルが共有アセットのパスを指定した場合は、その指定を優先する。

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Ubuntu+Sans:wght@400;500;700&family=Noto+Sans+JP:wght@400;500;700&family=Ubuntu+Mono:wght@400;700&display=swap" rel="stylesheet">
<link rel="stylesheet" href="./design-system/document.css">
<script src="./design-system/theme.js"></script>
<script src="./design-system/math-copy.js"></script>
<script async src="https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-mml-chtml.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/highlight.js/11.11.1/highlight.min.js"></script>
<script>document.addEventListener("DOMContentLoaded", () => hljs.highlightAll());</script>
```

主要規則は次のとおり。

- 背景は `#FAF9F6`。部品は白地、黒罫線、角丸を基本とする
- 自然言語は Ubuntu Sans と Noto Sans JP、コード・URL・日付は Ubuntu Mono を使う
- 有彩色はリンク青 `#2990DA` とアクセント赤 `#D63A2F` に限定する
- 上の色はライト表示の値である。ダーク表示では `document.css` が同じ役割の変数（`--mb-bg` など）を暗い配色へ置き換える
- 色は必ず `var(--mb-*)` で参照し、ページ側に色の直接指定を書かない（直接指定するとダーク表示で読めなくなる）
- 赤い強調は原則として 1 ページ 1 箇所までとする
- シンタックスハイライトとコード差分の色は、意味を区別する機能色としてこの制限の対象外とする
- 余白は上下左右の均衡を保つ
- 引用は `.mb-quote` を使い、原文と訳文を同じ文字サイズ・色で上下に並べる
- `.mb-chip` は並列の固有名や分類名の列挙にだけ使う
- 絵文字や矢印文字を図記号として使わない。必要な記号はインライン SVG で描く
- 表は短い対応関係に使い、3 列までを基本とする
- 行見出しのセルには `.mb-rowlabel` を付け、語中の折り返しを防ぐ
- コード差分は `pre.mb-diff` を使い、変更理由を散文で説明してから必要な断片を示す
- ページ固有の `<style>` は図の配置調整など最小限にとどめる

### ライト / ダーク表示

- `theme.js` を head 内で同期読み込み（`async` / `defer` なし）し、表示前にテーマを確定させる
- 既定は OS の設定（`prefers-color-scheme`）に従う。右上の切替ボタンで選んだテーマは `localStorage` に保存され、以後はそれが優先される
- 切替は `<html data-theme="light|dark">` で行う。HTML 側にこの属性を書かない
- 印刷と PDF は常にライト配色になる

## 構成とフォーマット

説明対象に合わせて、並置、図解、タイムライン、要約、折りたたみを使い分ける。
一方向の単純な手順を、必要性なくフローチャートにしない。

基本構成は次の順とする。

1. 背景と要点
2. 本論
3. 具体例
4. 補足・限界・関連事項

h1 とリード文の後に `.mb-toc` の目次を置き、各 h2 に対応する `id` を付ける。

### 用語リスト

専門用語は本文の初出で定義する。
用語リストは、複数箇所から参照する用語がある場合だけ設ける。
用語リストの位置は文書ごとに変更しない。
ブラウザ幅 1400px 以上では、本文右側の専用欄へ表示する。
ブラウザ幅 1399px 以下では、本文末尾へ表示する。
配置の切り替えは共有 CSS だけが担当し、用語リストによってヘッダー、リード、目次、要約、本文の幅を縮めてはならない。
マークアップは `aside.mb-glossary` と `dl`、`dt`、`dd` を使う。
正解例は `design-system/component-samples.html` を参照する。

## 図

- `.mb-figure` は、画像・SVGなどの視覚資料とキャプションを一つにまとめる外枠である。特定の図形や「矢印で結んだ箱」を意味しない
- `.mb-figure-frame` は視覚資料の表示面、`figcaption` は図番号・説明・出所の表示領域として使う
- 原典に重要な図がある場合は、出所を明示して引用する
- 原典の図があるのに模倣図を作らない
- 自作図はインライン SVG とし、アスキーアートを使わない
- 黒一色の線画を基本とし、`.mb-figure-frame` に載せる
- SVG の色は `#111110`（線・文字）、`#FFFFFF`（面の塗り）、`#DFDFDF`（薄い線）、`#595959`（補助の文字）、または `currentColor` だけを使う。`document.css` がダーク表示時にこれらをテーマ色へ置き換える。これ以外の色を書くとダーク表示で追従しない
- ノード数が多い場合は縦方向を優先する
- 矢印が交差する構成を避ける
- 単なる直列手順は番号付きの説明として表現する

## コード

- Highlight.js を必ず読み込み、言語に応じたシンタックスハイライトを適用する
- `pre code` には `language-javascript`、`language-python`、`language-html` などの言語クラスを必ず付ける
- ハイライトしないテキストには `language-plaintext` を付ける
- 独自の色付けでコードを装飾せず、`document.css` の `.hljs-*` 規則を使う
- `pre.mb-diff code` には `nohighlight` を付け、差分専用の色と行頭記号を使う

## 数式

- MathJax 3 を使う
- インライン数式は `$...$`、ディスプレイ数式は `$$...$$` とする
- ベクトルと行列は `\boldsymbol{...}` を使う
- スカラー、添字、集合名は装飾しない
- 名前付きの演算は `\mathtt{...}`、標準 LaTeX コマンドはそのまま使う
- `math-copy.js` により、すべての数式から LaTeX 原文をコピーできるようにする
- ページ側で `window.MathJax` を再定義しない
- 未知のコマンドを別記法へ勝手に置換しない

## 仕上げの点検

HTML を書き終えたら、ユーザーに渡す前に必ず次の工程を行う。新規作成でも既存ファイルの修正でも省略しない。

1. `stop-ai-slop-jp` スキルを読み込み、本文、見出し、表、図中の文字、キャプション、用語リストのすべてを対象に、クイックチェックの項目を確認して、見つかった箇所を直す
2. 「レポート単体で読める文章にする」の規則に照らし、会話の経緯、依頼者への呼びかけ、作業者の視点の語が残っていないか確認し、残っていれば書き直す。`grep` で「あなた」「今回」「先ほど」「途中」「撤回」「前回」「ご指摘」などを検索するとよい
3. 直した点と、確認できなかった点をユーザーへの報告に書く。点検の経緯は HTML には書かない

## 印刷と PDF

印刷対応は `document.css` の `@media print` を使う。印刷時はダーク表示中でもライト配色に戻り、切替ボタンは表示しない。
PDF 化はユーザーから明示的に依頼された場合だけ `render-pdf.sh` を実行する。
