# タスクを issue に分ける

`docs/design/` の設計やタスクの一覧（TASKS.md など）を、issue-loop が1つずつ進められる issue に分けます。タスクの一覧の1行だけでは実装の前提が足りないので、issue には要件と完了要件を細かく書きます。

## 手順

1. **元の文書を読む。** 指定された文書と、そこから参照される `docs/design/` の章、`docs/README.md` の用語表、CLAUDE.md を読む。すでにある issue（`gh issue list --state all --limit 500 --json number,title,state`）と重ならないかも見る。

2. **分ける。** 1つの issue は1つの PR で終わる大きさにする。
   - 目的が1つで、レビューで全体を読み切れる量（変えるファイルが20前後まで）にする。
   - 足場（設定やディレクトリ）、データの形（モデル、マイグレーション）、API、画面、インフラは、別の issue に分ける。
   - 先に要るものを依存として書く。依存のない issue が並んでいれば、ループはそれらを順に進められる。

3. **本文を書く。** `.github/ISSUE_TEMPLATE/task.yml` と同じ見出しにする。ループは「### 依存する issue」の見出しの下の `#番号` を読むので、見出しの文字を変えない。

   ```markdown
   ### 背景

   <なぜ要るか>

   ### 要件

   - <作るもの、変えるもの。ファイル、API、画面の名前>

   ### 完了要件

   - [ ] <テストかコマンドで確かめられる条件>

   ### 対象外

   - <この issue ではやらないこと>

   ### 依存する issue

   #12, #13（なければ「なし」）

   ### 参照する設計文書

   - docs/design/architecture.md の 3.1
   ```

   - 完了要件は、テストやコマンドで確かめられる形にする（例：「`uv run pytest backend/apps/rooms` が通る」「ルームのメンバーでない利用者が POST すると 404 を返すテストがある」）。
   - 設計文書の内容は、要る部分を要約して書き、章を参照に挙げる。設計にないことを足さない。決まっていないことは「未確定」と書き、issue を分けるか、人に尋ねる。
   - 公開リポジトリなので、アカウント ID、メールアドレス、秘密の値を書かない。

4. **人に確かめる。** 登録する前に、題名、依存、完了要件の数を表にして見せ、了承を得る。issue の作成は公開リポジトリへの書き込みなので、了承なしに作らない。

5. **登録する。** 依存される側から順に作り、作った番号で後の issue の「依存する issue」を埋める。

   ```bash
   gh issue create --title "<日本語の題名>" --body-file <本文のファイル> --label loop:ready
   ```

   `loop:ready` を付けると CodeRabbit が Coding Plan を自動で作り始める。すぐにループへ渡したくない issue には付けない。

6. **報告する。** 作った issue の番号と題名、依存の関係、`loop:ready` を付けなかったものを伝える。
